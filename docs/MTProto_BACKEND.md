# WaysGram MTProto backend integration

## Target layout

The original Telegram Android client speaks MTProto, not the WaysGram REST API. The supported architecture therefore separates the OTP delivery service from the message server:

- **AuthWaysGram_bot / AuthBot on Bothost** — issues virtual +1XXXXXXXXXX identifiers, verifies that the bot user owns them, and delivers a code generated by the MTProto server.
- **Self-hosted MTProto server** — owns MTProto auth, user IDs, sessions, chats, groups, channels, media, and updates. Its public listener must be reachable by the Android client over raw TCP.
- **Android client** — keeps the original LoginActivity, LaunchActivity, navigation and Telegram screens. Its native connection layer must be configured to trust the MTProto server's RSA public key and map DC IDs to that server without adding a server-selection screen.

AuthBot is an OTP delivery bridge. It does not create an MTProto authorization key and does not validate auth.signIn.

## AuthWaysGram_bot delivery bridge

The current AuthBot endpoint is:

~~~text
POST https://bot-1793554244-6434-weterochina.bothost.tech/v1/otp/deliveries
~~~

The endpoint verifies the HMAC-SHA256 signature, request timestamp, purpose, six-digit code, idempotency key and assigned/verified virtual number. It stores the code encrypted and sends it through @AuthWaysGram_bot. It accepts the number in either of the representations used by clients and telesrv:

- +1XXXXXXXXXX
- 1XXXXXXXXXX (11 digits, no leading plus)

The second form is normalized to the first before the Bot database lookup. Other country prefixes are rejected.

Configure the AuthBot environment on Bothost:

~~~env
TELESRV_OTP_WEBHOOK_SECRET=<long-random-secret>
~~~

Configure the MTProto server with the same secret:

~~~env
TELESRV_PHONE_CODE_DELIVERY_PROVIDER=webhook
TELESRV_PHONE_CODE_LENGTH=6
TELESRV_OTP_WEBHOOK_URL=https://bot-1793554244-6434-weterochina.bothost.tech/v1/otp/deliveries
TELESRV_OTP_WEBHOOK_SECRET=<same-long-random-secret>
~~~

The user must first obtain and verify a virtual number in @AuthWaysGram_bot, then enter that same number on the original phone-number login screen. The MTProto server generates and verifies the six-digit code; AuthBot only delivers it. Do not use this webhook for official Telegram login codes.

## Hosting boundary

Bothost's published domain documentation describes an HTTPS reverse proxy on external port 443 that forwards requests to one selected port inside a container. It documents HTTP/web-service traffic, not arbitrary raw TCP port forwarding. See the [Bothost domains and ports guide](https://bothost.ru/docs/domains-and-ports).

The self-hosted MTProto server needs a public TCP listener (OwpenGram/telesrv defaults to TCP port 2398). Therefore:

- Bothost is suitable for the AuthBot REST API and signed OTP webhook.
- Do not assume the Bothost HTTPS domain is itself an MTProto TCP endpoint.
- Place the MTProto server on a host that exposes raw TCP, or obtain explicit confirmation from Bothost that a raw TCP port can be forwarded to the container.

The MTProto server's HTTPS/web/admin endpoint and its raw MTProto TCP endpoint are separate transport requirements. A normal HTTPS reverse proxy does not automatically forward native MTProto TCP.

## Android client integration required

The source repository currently preserves the upstream Telegram login and UI files. The following native connection work remains separate from the OTP webhook:

1. Configure the original client's native DC routing to use the self-hosted MTProto host and port.
2. Install the server's RSA public key/fingerprint into the MTProto handshake trust path.
3. Keep this configuration hidden and fixed for WaysGram; do not add a server-selection screen or replace the login screen.
4. Map all DC IDs used by the client to the single-server endpoint (including media/download DC routes) if the backend uses one physical server.
5. Validate login, session persistence, profile, dialogs, messages, media, updates, groups, channels, and other RPCs against the pinned Telegram Android layer before shipping an APK.

The open-source OwpenGram Android fork demonstrates the underlying native configuration pattern through native_applyServerConfig, but its full multi-server UI is not being copied into WaysGram. Only a hidden, single-server configuration path is relevant.

## Existing REST data is not automatically migrated

The AuthBot SQLite database is currently a separate WaysGram REST data model. Its account IDs, profile rows, REST messages, groups, channels, media, balances, gifts, and internal bot records do not automatically become MTProto users or messages.

When the MTProto server becomes authoritative for the original Telegram screens, existing REST records need an explicit migration and identity mapping. Do not assume changing a database URL or enabling the OTP webhook transfers that data.

## Current implementation status

- Original Telegram startup, login UI, main tabs, gift UI and launcher icon are preserved in WaysGram-source.
- AuthBot supports signed MTProto OTP delivery at /v1/otp/deliveries.
- Retry handling preserves the issued OTP after transient Bot API or rate-limit failures.
- The webhook accepts telesrv's digit-only phone format and canonicalizes it to the Bot's +1XXXXXXXXXX number.
- MTProto DC/RSA configuration has not yet been ported into the pinned WaysGram Android source.
- A completed and signed APK has not yet been verified from the latest Android workflow run.
